The Playwright MCP server acts as a bridge — it exposes Playwright's browser automation capabilities (navigate, click, fill, screenshot, evaluate) as "tools" that Claude can invoke during a conversation. When Claude needs to see what is on a page, it takes a snapshot. When it needs to click a button, it sends a click command through the MCP server. When it needs to verify that an element appeared after an action, it asserts visibility through the MCP server. This means Claude is not guessing about your application's DOM structure — it is observing it in real time, just as you would if you were writing tests manually.</p>

  <p>The conversation itself is where the SDET's skill in prompt engineering determines the quality of the output. A poor prompt produces a poor test. A well-crafted prompt produces a test that needs minimal refactoring. Here is the real-world difference. <strong>Poor prompt:</strong> "Write Playwright tests for the login page." Claude will generate something — but the locators will be generic, the assertions will be minimal (probably just URL checks), and the test structure will be flat with no Page Object Model. <strong>Effective prompt:</strong> "I need a Playwright test that: (1) navigates to https://staging.myapp.com/login, (2) verifies the login form is visible with email field, password field, and sign-in button, (3) enters invalid credentials and asserts the error message 'Invalid email or password' appears with role='alert', (4) enters valid credentials and asserts navigation to /dashboard, (5) uses role-based locators and test-id attributes where available, (6) wraps everything in a test.describe block with beforeEach for navigation, (7) exports a LoginPage page object class at the bottom of the file with methods for navigate, login, and assertError. Do not generate the test yet — first, take a snapshot of the login page at https://staging.myapp.com/login and confirm the locator strategy before you write code." This prompt produces dramatically better output because it specifies: the application URL, the exact UI elements to verify, the specific error message with its ARIA role, the expected navigation, the locator strategy preference, the test structure requirements, and — critically — it asks Claude to inspect the page before generating code. The principle is: <strong>AI generates better tests when you make it observe before it writes.</strong></p>

  <h2>GitHub Copilot, Cursor, and the AI-Native SDET Toolchain</h2>

  <p>Claude Code with Playwright MCP is the deep-work tool for generating complete test files from natural-language descriptions.   <h3>GitHub Copilot — Inline Test Acceleration</h3>

  <p>Copilot is the AI assistant that works at the keystroke level — it suggests completions as you type, responds to natural-language comments, and (in agent mode) can generate entire functions and test blocks. For SDETs, Copilot's primary value is <strong>acceleration of the mechanical parts of test writing</strong>. When you type <code>// test that the search returns results matching the query</code> in a Playwright test file, Copilot suggests a complete test block — navigating to the search page, typing a query, asserting that results appear, and verifying the result count is greater than zero. The suggestion is not always correct — Copilot may use outdated locators or miss edge cases — but it eliminates the mechanical work of typing out boilerplate test structure. Mitchell's approach with Copilot, honed over thousands of test files at Asda and the Co-op, is: <strong>accept the structure, review the details.</strong> Copilot is excellent at generating the skeleton — <code>test.describe</code>, <code>test.beforeEach</code>, <code>await page.goto()</code>, the basic action-assertion flow. It is less reliable at choosing the right locators (it tends to default to CSS selectors unless prompted otherwise) and at generating assertions that reflect the actual business logic. The SDET's role is to accept the structure that Copilot generates, then manually rewrite the locators to use role-based or test-ID-based selectors and adjust the assertions to match the acceptance criteria.</p>

  <p>In a 2026 interview, you should be able to describe your Copilot workflow concretely: "I use Copilot for test scaffolding — when I write a comment describing a test scenario, Copilot generates the test skeleton. I accept the structure but I always review and often replace: locators (I enforce role-based selectors), assertions (I add assertions at every state transition, which Copilot often misses), and test data (I replace Copilot's hardcoded values with parameterised test data factories). I have a <code>.github/copilot-instructions.md</code> file in every repository that tells Copilot to use role-based locators, to include accessibility assertions where relevant, and to wrap related tests in <code>test.describe</code> blocks with <code>beforeEach</code> hooks — which dramatically improves the quality of the initial suggestions." That answer demonstrates that you do not just use Copilot — you have configured it, you understand its failure modes, and you have a review process. That is what senior interviewers want to hear.</p>

  <h3>Cursor — The AI-Native IDE for Test Automation</h3>

  <p>Cursor is an AI-native code editor (built on VS Code) that goes beyond inline suggestions. Its key features for SDETs: <strong>Tab</strong> (multi-line edits that intelligently predict what you want to change across multiple locations), <strong>Cmd+K</strong> (inline code generation and editing — highlight a comment, press Cmd+K, describe what you want, and Cursor generates or edits the code in place), <strong>Composer</strong> (multi-file generation — describe a feature and Cursor creates multiple files simultaneously, ideal for generating a Page Object Model with page objects, test specs, and utility files in one prompt), and <strong>.cursorrules</strong> (a project-level configuration file that defines coding standards, locator preferences, test patterns, and framework conventions that Cursor applies to every AI interaction). For SDETs building test frameworks from scratch, Cursor's Composer is transformative: you can describe a complete test framework architecture — "a Playwright test framework with a base Page Object class, an auth fixture that stores session state, a test data factory with faker.js, and five test specs for the checkout flow" — and Cursor generates all the files simultaneously, with cross-file references, consistent naming, and imports already wired up.</p>

  <p>The interview-relevant detail about Cursor is not that it exists — it is how you configure it for test-specific quality. Mitchell's <code>.cursorrules</code> for testing projects includes: "Always use Playwright's role-based locators (<code>getByRole</code>, <code>getByLabel</code>, <code>getByText</code>) before CSS or XPath. Always include ARIA assertions where applicable. Never use <code>page.waitForTimeout</code> — rely on Playwright's auto-waiting. Structure every test file as: imports, test.describe with a clear name, test.beforeEach for navigation, individual test blocks for happy path and edge cases. Always export page objects at the bottom of the file. Use <code>expect().toBeVisible()</code> for visibility checks — never <code>expect().toBeTruthy()</code>." When you mention a <code>.cursorrules</code> file in an interview, you are signalling that you do not just use AI tools — you configure them, you enforce quality standards through them, and you think about AI-assisted testing as an engineering discipline, not a magic trick. At Nationwide, Mitchell's team achieved a 40% reduction in code review comments on AI-generated tests after implementing a project-level <code>.cursorrules</code> file — because the AI-generated code already conformed to the team's standards before human review began.</p>

  <h3>Playwright MCP — Why It Matters Beyond Claude Code</h3>

  <p>The Model Context Protocol is not exclusive to Claude Code — it is an open standard that is being adopted across the AI ecosystem. Understanding MCP is important for 2026 SDET interviews because it represents a fundamental shift in how AI tools interact with testing infrastructure. An MCP server exposes a set of tools (navigate, click, fill, screenshot, evaluate, assert) that any MCP-compatible AI client can use. This means the same Playwright MCP server that Claude Code uses can also be used by Cursor, by a custom AI testing agent, or by a CI-integrated test generation service. The architectural implication for test automation is significant: <strong>the testing tools become the interface, and the AI model becomes replaceable.</strong> You can switch from Claude to Gemini to a local open-source model — as long as they all speak MCP, they all connect to the same Playwright server with the same capabilities. This architecture makes AI-assisted testing vendor-agnostic and future-proof — which is exactly the kind of strategic thinking that senior SDET interviews reward.</p>

  <p>In your interview, when the panel asks about Playwright MCP, do not just say "it is a way to connect Claude to Playwright." Say: "MCP is Anthropic's open protocol for connecting AI models to external tools. The Playwright MCP server exposes browser automation as AI-callable tools, which means any MCP-compatible AI client — Claude Code, Cursor, or a custom agent — can navigate, interact with, and assert on web applications. Architecturally, this decouples the AI model from the testing infrastructure: the MCP server is the stable interface, and the AI model behind it can evolve independently. From a test strategy perspective, this means my AI-assisted testing workflow is not locked into any single AI provider — as better models emerge, I plug them into the same MCP server and they work with the same Playwright capabilities." That answer demonstrates architectural thinking — which is what distinguishes senior SDETs from test writers.</p>

  <h2>AI vs Human — Evaluating, Reviewing, and Knowing When to Override</h2>

  <p>The ability to generate tests with AI is not the skill that gets you hired — it is the ability to <strong>judge</strong> AI-generated tests that matters. Every AI coding assistant produces output that looks plausible on the surface but contains subtle errors that only an experienced SDET can spot. In 2026 interviews, the "AI vs human review" question is rapidly becoming a staple — and the candidates who can articulate a systematic review framework are the ones who get offers. Here is the framework you should describe in your interview.</p>

  <div class="challenge-grid">
    <div class="challenge-card">
      <h3>What AI Gets Right — And How to Leverage It</h3>
      <p>AI coding assistants excel at: <strong>test structure</strong> — they reliably generate properly formatted <code>test.describe</code> blocks, <code>beforeEach</code> hooks, and <code>test()</code> blocks with correct async/await syntax — the boilerplate that experienced SDETs find tedious but junior SDETs often get wrong. <strong>Locator suggestions</strong> — when prompted correctly (with context about locator hierarchy), AI tools suggest reasonable locators based on visible text and roles. <strong>Assertion patterns</strong> — AI knows the common assertion patterns for web testing: visibility checks, URL checks, text content checks, element count checks. <strong>Code consistency</strong> — AI generates tests with consistent formatting, naming conventions, and structural patterns — which matters in large test suites where multiple SDETs contribute. <strong>Test data variety</strong> — AI can generate diverse test data (names, emails, addresses) that covers more input combinations than a human would think to include. The key insight for interviews: AI is strongest at the <em>mechanical</em> aspects of test writing — the parts that require knowledge of syntax and patterns but not domain understanding. The SDET's value is in the <em>semantic</em> aspects — understanding what the application should do and whether the test actually verifies that behaviour.</p>
    </div>

    <div class="challenge-card">
      <h3>Common AI-Generated Test Failures — The Patterns You Must Recognise</h3>
      <p>Mitchell has reviewed thousands of AI-generated tests and identified recurring failure patterns that every SDET must recognise. <strong>Pattern 1: The Hallucinated Assertion.</strong> AI generates an assertion like <code>expect(page.getByText('Order confirmed')).toBeVisible()</code> — but the application displays "Your order has been placed" instead. The assertion passes locally if the AI also generated the test data, but it does not verify the actual user-facing text. <strong>Pattern 2: The Pass-through Test.</strong> AI generates a test that navigates to a page, fills a form, submits it, and asserts... nothing meaningful. The test "passes" because it did not assert on the outcome — it only verified that no errors were thrown. This is the most dangerous AI-generated test pattern because it creates false confidence. <strong>Pattern 3: The Brittle Locator.</strong> AI defaults to CSS class selectors like <code>.btn-primary-large-v2</code> when not explicitly instructed otherwise. These selectors break the moment the design system updates its class naming. <strong>Pattern 4: The Missing Cleanup.</strong> AI generates a test that creates a resource (a user, an order, a configuration) but does not clean up after itself — leaving test pollution that causes subsequent tests to fail intermittently. <strong>Pattern 5: The Silent Skip.</strong> AI wraps interactions in try-catch blocks or uses conditional logic that silently skips assertions when conditions are not met — producing a green test result that masked a real failure. In your interview, describing these failure patterns by name — "I watch for hallucinated assertions, pass-through tests, and brittle locators in every AI-generated test I review" — signals that you have genuine experience with AI-assisted testing, not just theoretical knowledge.</p>
    </div>

    <div class="challenge-card">
      <h3>The Human Review Checklist — Your Interview-Ready Framework</h3>
      <p>Every AI-generated test in Mitchell's teams goes through a seven-point review checklist before merge. Memorise this checklist for your interview — and be prepared to walk through each point with a concrete example. <strong>1. Locator audit:</strong> Are all locators role-based, label-based, or test-ID-based? Upgrade any CSS-class-based locators. <strong>2. Assertion audit:</strong> Does every user action have a corresponding assertion? Does every state transition (navigation, form submission, modal open/close) have a verification? <strong>3. Data audit:</strong> Is any test data hardcoded? Does the test depend on specific data that might not exist in CI? Replace with test data factories or API seeding. <strong>4. Isolation audit:</strong> Can this test run in any order? Does it create state that subsequent tests depend on? Add cleanup in <code>afterEach</code> or use API-driven teardown. <strong>5. Flakiness audit:</strong> Are there any <code>waitForTimeout</code> calls? Any assertions on timing-dependent content (e.g., "3 seconds ago")? Replace with auto-waiting assertions. <strong>6. Coverage audit:</strong> Does this test cover the happy path, the key failure modes, and at least two edge cases? If not, supplement with additional test blocks. <strong>7. Readability audit:</strong> Would a new team member understand what this test verifies within thirty seconds of reading it? If not, improve the test names, add comments explaining the scenario, and ensure the assertions read like acceptance criteria. In your interview, say: "I apply a seven-point review checklist to every AI-generated test: locator, assertion, data, isolation, flakiness, coverage, and readability. This ensures that AI-generated tests meet the same quality standard as human-written tests — and it is a checklist I have refined over hundreds of code reviews."</p>
    </div>

    <div class="challenge-card">
      <h3>When to Reject an AI-Generated Test Entirely</h3>
      <p>Some AI-generated tests should not be fixed — they should be rejected and rewritten. Knowing when to reject is a sign of seniority. Reject when: the test verifies the wrong behaviour (AI misunderstood the requirements and a rewrite is faster than a fix), the test structure is fundamentally wrong (flat tests when the team uses Page Object Model, no test isolation, hardcoded environment URLs), the locator strategy is unrecoverable (every locator is a CSS class that will break — rewriting locators is faster than fixing twenty of them), or the test is over-engineered (AI generated a fifty-line test with loops and conditionals for something that should be a ten-line linear test). The interview signal: "I reject approximately 10-15% of AI-generated tests outright — not because AI is bad, but because rewriting from a clear understanding of the requirements produces better tests in less time than patching a fundamentally flawed scaffold. Knowing when to start over is as important as knowing how to review."</p>

  <h2>Prompt Engineering for Test Automation — The Meta-Skill Hiring Managers Value Most</h2>

  <p>Every AI coding assistant — Claude Code, Copilot, Cursor, ChatGPT — is a prompt-driven system. The quality of the test it generates is directly proportional to the quality of the prompt you provide. Prompt engineering for test automation is therefore the meta-skill that amplifies the effectiveness of every other AI tool in your SDET toolchain. In 2026 interviews, you will increasingly be asked: "How do you write prompts for test generation?" — and a vague answer like "I describe what I want and it works" will not cut it. Here is the structured approach that Mitchell teaches SDETs preparing for senior interviews.</p>

  <div class="challenge-grid">
    <div class="challenge-card">
      <h3>The Four-Element Prompt Template for Test Generation</h3>
      <p>Every effective test-generation prompt contains four elements: <strong>Context</strong> (the application under test, the testing framework, the project conventions), <strong>Specification</strong> (the exact user journey to test, step by step, including expected outcomes at each step), <strong>Constraints</strong> (locator preferences, naming conventions, structural patterns, what NOT to do), and <strong>Verification</strong> (ask the AI to inspect the page first, or to explain its locator choices before writing code). A prompt that contains all four elements produces output that is 60-80% closer to production-ready than a prompt that only contains the specification. Mitchell's template: "Context: We use Playwright with TypeScript, Page Object Model, and role-based locators. The <code>.cursorrules</code> file in the repo defines all conventions. Specification: Test the checkout flow — (1) add item to basket from product page, (2) navigate to basket and verify item appears, (3) proceed to checkout, (4) fill delivery details, (5) select payment method, (6) confirm order, (7) assert order confirmation page with order number. Constraints: Use role-based locators exclusively, no CSS classes, no <code>waitForTimeout</code>, all test data from the <code>testDataFactory</code> utility, <code>beforeEach</code> for navigation, <code>afterEach</code> for cleanup. Verification: Before generating code, navigate to the product page, take a snapshot, and report the locator strategy you will use for each interactive element."</p>
    </div>

    <div class="challenge-card">
      <h3>Chain-of-Thought for Test Design</h3>
      <p>Chain-of-thought prompting — asking the AI to reason step by step before generating output — is as effective for test design as it is for general problem-solving. Instead of "Write a Playwright test for user registration," prompt: "I need a Playwright test for user registration. Before you write any code, think through: (1) What are the preconditions? (Is the user already logged in? Do we need to clean up from previous tests?) (2) What are the state transitions? (Landing page → registration form → validation errors → successful registration → redirect) (3) What assertions are needed at each transition? (Form visibility, error message content, success message, URL change) (4) What can go wrong? (Email already taken, password too weak, network failure during submission) (5) What is the locator strategy for each element? Report your reasoning, then generate the test." This forces the AI to consider edge cases, test structure, and assertion coverage before writing a single line of code — and the resulting test is dramatically more thorough than one generated from a one-line prompt.</p>
    </div>

    <div class="challenge-card">
      <h3>Few-Shot Prompting — Teaching the AI Your Team's Style</h3>
      <p>Few-shot prompting means providing examples of the output you want before asking the AI to generate new content. For test automation, this means including one or two existing test files from your project in the prompt — showing the AI exactly how your team structures tests, names variables, formats assertions, and organises Page Objects. The prompt: "Here are two test files from our project that demonstrate our testing patterns and conventions. [Paste two test files.] Using these exact patterns — same structure, same naming conventions, same assertion style, same locator strategy — generate a test for the 'forgot password' flow. The test should be indistinguishable from a test written by our team." This technique is particularly effective in Cursor, where you can @-mention existing test files in your Composer prompt to use them as style references. In your interview, describing how you use few-shot prompting shows that you have moved beyond "AI writes my tests" to "I teach AI to write tests the way my team writes tests" — a distinction that hiring managers notice.</p>
    </div>

    <div class="challenge-card">
      <h3>The "Break It" Prompt — Using AI for Negative Testing</h3>
      <p>One of the most powerful — and under-discussed — uses of AI in test automation is generating negative test scenarios. Humans are notoriously bad at thinking of everything that could go wrong; AI, when prompted correctly, can generate exhaustive negative test cases. The prompt pattern: "Here is a user registration form with fields: name (required, 2-50 chars), email (required, valid email format), password (required, 8+ chars, must include uppercase, lowercase, number, special char), age (required, 18-120). Generate negative test cases that cover: boundary values (just below and just above each limit), invalid formats for email, missing required fields, SQL injection attempts, XSS payloads, Unicode edge cases, extremely long inputs. For each test case, include the input values, the expected error message, and the expected behaviour (form should not submit, specific field should show error). Generate these as Playwright test blocks." AI produces twenty or thirty negative test cases in seconds — many of which a human SDET would not think of. Describing this technique in an interview demonstrates that you use AI not just for productivity but for <em>quality improvement</em> — uncovering edge cases that manual test design might miss.</p>
